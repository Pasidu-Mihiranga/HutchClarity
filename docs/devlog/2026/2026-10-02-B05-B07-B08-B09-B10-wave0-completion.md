## Decisions made

- **The `full` profile requires PostgreSQL.** It used to accept a SQLite URL, which loaded the simulated world but left Clarity's own state in memory: it looked like success and gave a deployment two replicas could not share. Now refused, with the reason and the alternative in the message.
- **The application does not run as the database owner.** A superuser bypasses row-level security unconditionally, so policies written while connecting as one are decorative. Requests run as `clarity_app`, a `NOBYPASSRLS` role that is a member of every module role, so its reach is exactly the union of the per-module grants.
- **Row-level security checks writes as well as reads.** A request bound to one subscriber cannot store a record belonging to another, because a request that could write rows it cannot read would be a way to plant data under another customer.
- **A conflict is reported wherever the driver detects it.** The in-memory driver is optimistic and refuses at commit; PostgreSQL takes a row lock and refuses at the write. The parity suite asserts the guarantee (a typed conflict, never a silent overwrite) rather than the statement that raises it, so one suite covers both.
- **A bounded `lock_timeout`.** Blocking forever on a money path is worse than failing, so the wait is 250ms and a timeout becomes `ConcurrentUpdate`.
- **Log redaction does not reuse `clarity.ai.pii`.** That module tokenises reversibly for model calls and sits a layer above (I4); log redaction is irreversible and applies to every line. A test asserts the two agree on what a number looks like.
- **Licence exceptions carry reasons, not just names**, and the gitleaks allowlist holds the exact verified strings rather than file paths, so the rule keeps working elsewhere in the same files.

## Bugs this work exposed

The parity suite and the two-replica test did their job. Each of these would have been invisible in the lite lane.

1. **Two replicas each claimed every plan.** The first version of the driver skipped the version check for any row it had written, on the reasoning that a write holds a row lock. True for a row that exists; false for one that does not, because there is no row to lock. Two units of work both found a key absent, both inserted, and the second silently overwrote the first. For a claim ("execute this plan only if nobody has") that is the plan running twice. The driver now version-checks inserts and requires the inserter to find version 1, its own.
2. **The parity suite hung against PostgreSQL.** Several tests deliberately leave a unit of work open to show a write is invisible before commit; on a real connection that holds locks, and teardown's `DROP SCHEMA` waited for them forever. The fixture now tracks and rolls back every unit it hands out.
3. **Row-level security did nothing**, because the app connected as the database superuser. Fixed by the application role above.
4. **In-place mutations were lost on a copying driver.** `CaseService` mutated a record and returned without saving; the in-memory driver returns the same object so it worked, while PostgreSQL returns a copy and the case never left `OPEN`. Every mutating method now writes the record back, and `evaluate` works on one record instance rather than calling `build_timeline`, which loaded a second copy and left the caller's stale.
5. **The venv was broken**: `.venv/bin/python` was a stale symlink to Homebrew 3.12 while `pyvenv.cfg` and the console scripts were 3.14, so any Makefile target calling `python` directly could not import `clarity`. Repointed, and `make setup` now passes `--clear` so it cannot recur.
6. **A test fixture caused unbounded recursion.** The tracing fixture saved and restored the global tracer provider; before anything sets one that global is a `ProxyTracerProvider` whose job is to delegate to the same global, so restoring it made it delegate to itself.
